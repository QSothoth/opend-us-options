# 港股期权异动「近月只有 9 月」独立审计

- **审计对象**：`get_option_event(HK_SECURITY)` 一年异动里，真实近月（到期 ≤14 日 / ≤5 日）为何几乎只出现在 2026-09。
- **审计时间 / 数据基准日**：2026-09-20（OpenD 服务端“今天”）。
- **方式**：只读 OpenD（`127.0.0.1:11111`），重新分页拉取、三角校验、对照官方文档与本地 SDK，不下单。
- **一句话结论**：**不是我们算错，也不是过滤写错；是接口归档只保留“当前仍挂牌”的合约，历史月份的近月合约到期后整批消失。结论选 C。** 但接口 `dte` 字段确实有坑（相对“今天”漂移），这是另一个必须知道的陷阱。

## 3. 三角校验到期日：谁对谁错

三个来源：

1. 接口 `strike_time`；
2. 期权代码里的 `YYMMDD`（如 `HK.XIC260929C6250` → 26-09-29）；
3. 接口 `dte` 字段。

**结果：**

- `strike_time` 与代码 `YYMMDD`：**1719/1719 完全一致**（0 处冲突）。两个独立来源互相印证，到期日可信。
- 接口 `dte` **等于** `到期日 − 2026-09-20（今天）`：**1719/1719 命中**。
- 接口 `dte` **等于** 成交日到期的真实天数：**0/1719 命中**。

**具体反例（成交日很早）：**

| option_code | 成交时间 | strike_time | 代码 YYMMDD | 接口 dte | 真实 DTE（成交日→到期） |
|---|---|---|---:|---:|---:|
| `HK.XIC260929C6250` | 2025-09-24 10:10:11 | 2026-09-29 | 260929 | **9** | **370** |
| `HK.ALB260929C185000` | 2025-09-24 10:42:20 | 2026-09-29 | 260929 | **9** | **370** |
| `HK.TCH260929C680000` | 2025-10-02 10:32:15 | 2026-09-29 | 260929 | **9** | **362** |
| `HK.PEN260929C70000` | 2026-03-31 11:18:12 | 2026-09-29 | 260929 | **9** | **182** |

**结论：**

- 我们（扫描器）用 `fill_time + strike_time` 算的 `dte_at_fill` **是对的**。
- 接口 `dte` **是错的（对回放而言）**：它是“相对今天还有几天到期”，会随日期每天漂移（今天 9，明天 8，后天 7……）。
- 谁对谁错：**代码 YYMMDD 和 strike_time 对；接口 `dte` 不能用于历史回放。** 扫描器源码顶部已明确写了 “OpenD's `dte` column is NOT used for historical replay (it drifts)”，实现也照做了，未踩坑。

## 4. 关键证据：归档里只有“今天仍挂牌”的到期日

把全类型（CALL/PUT × BUY/SELL/NEUTRAL，不加任何 side/action 过滤）一年数据拉下来，去重后 **6073 条**，它们只覆盖 **9 个到期日**：

| 到期日 | 异动条数 |
|---|---:|
| 2026-09-18（上周五，刚到期） | 134 |
| 2026-09-25 | 74 |
| 2026-09-29 | 2552 |
| 2026-10-29 | 736 |
| 2026-11-27 | 423 |
| 2026-12-30 | 1355 |
| 2027-03-30 | 448 |
| 2027-06-29 | 289 |
| 2027-09-29 | 62 |

这 9 个到期日，**正好就是 2026-09-20 当天港交所挂牌的期权到期日集合**。核对 `get_option_chain("HK.00700")`（腾讯，逐 30 天窗口取）：

- 期权链到期日：`2026-09-18, 2026-09-25, 2026-09-29, 2026-10-29, 2026-11-27, 2026-12-30, 2027-03-30`（更远的 2027-06/09 因限频未取全）；
- 异动归档到期日：上面 9 个全部包含；
- 期权链里有、异动里没有的：**0 个**。

**含义**：港交所股票期权每个月都有到期合约。如果归档是“历史完整”的，2025-10 的异动就应该出现 2025-10、2025-11、2025-12… 的到期日。实际一条都没有，只有那些**活到今天**的长到期合约。

对腾讯（`HK.00700`）单独拉一年，到期日集合也是这 9 个，没有 2025-10～2026-08 的任何月合约：

```
HK.00700: 323 条, 成交日 2025-10-02..2026-09-18
distinct expiries: 2026-09-18, 2026-09-25, 2026-09-29, 2026-10-29,
                   2026-11-27, 2026-12-30, 2027-03-30, 2027-06-29, 2027-09-29
```

→ **归档是按“合约当前是否仍挂牌”过滤的，已到期合约的异动被整批清掉。**

## 7. 服务端 `EXPIRY_DAYS` 的坑：会制造“假近月”

`EventIndicatorType.EXPIRY_DAYS` 是“距到期天数”区间筛选。但它按**今天**计算，不按成交日：

- 用 `EXPIRY_DAYS ∈ [0,14]` 拉 CALL BUY：`all_count=666`，返回行的到期日**只有 2026-09-25 和 2026-09-29**；
- 这 666 条里，接口 `dte` 是 5～9，但**真实成交时 DTE 最高 370 天**；
- 其中 **620 条**属于“接口 dte≤14 但真实 DTE>14”的**假近月**。

举例：`HK.TCH260929C680000`，成交 2025-10-02，接口 `dte=9`，真实 DTE=362 —— 它会被 `dte≤14` 的过滤条件当成“近月大单”，实际是一年前的 1 年期合约。

**同样地：**

- `EXPIRY_DAYS ∈ [0,5]` 和 `[0,7]` 返回完全相同的 26 条，都只有 2026-09-25；
- `EXPIRY_DAYS ∈ [0,30]` 和 `[0,14]` 返回相同的 666 条；
- → 该筛选粒度很粗，而且**只作用于“当前挂牌合约”**。

**危害**：
- 若回测把 `EXPIRY_DAYS` 或 `dte` 当近月条件，会**凭空造出 620 条假近月**，且全部堆在当前前月；
- 反过来，历史真正的近月事件（已到期合约）**一条也捞不回来**——既造假，又漏真。

**安全做法**：只用 `fill_time` + `strike_time`（或代码 YYMMDD）在客户端算 `dte_at_fill`。扫描器 `scan_hk_option_flow.py` 就是这么做的，未见此坑。

## 8. `MAX_DAY_NUM` / 分页 / 老数据是否被丢

**`MAX_DAY_NUM` 语义与上限**（`CALL BUY`，其余条件不变）：

| max_day_num | all_count | 最早成交 |
|---:|---:|---|
| 省略(None) | 1719 | 2025-09-24 |
| 0 | 47 | 2026-09-18 |
| 1 | 85 | 2026-09-17 |
| 7 | 244 | 2026-09-11 |
| 30 | 737 | 2026-08-19 |
| 90 | 1113 | 2026-06-22 |
| 180 | 1370 | 2026-03-23 |
| 364 | 1719 | 2025-09-24 |
| 365 | 1719 | 2025-09-24 |
| 500 / 730 / 1000 / 2000 / 5000 | **全是 1719** | 2025-09-24 |

- `MAX_DAY_NUM` 是“成交时间往前 N+1 天”的窗口，`0=当天, 1=近2天`（与官方文档一致）。
- **服务器归档上限约 365 天**：值 ≥364 后结果完全饱和，调再大也拿不到更早的数据。省略不传时默认给的就是这约一年。
- **没有“只保留大单远月”**：加不加 `OPTION_TYPE` 过滤都会拿到同样的合约集合；只是全类型条数更多（6131 vs 1719）。
- **没有分页丢老数据**：翻完所有页；另外用 `sort=TIME ASCEND` 逆序拉最老一页，最老仍是 2025-09-22，且那一页的到期日全是 2026-09-29 之后的远月，没有隐藏的旧近月。

**结论：** 服务器给多少，我们拿多少；老数据没被我们的分页吞掉。消失的是“服务器本来就不给”。

## 10. 对既有回测结论的影响

`threshold-study/universe_summary.csv` 里，四个方向的“近月样本”时间跨度全部只有 **2026-08-31 → 2026-09-18**；`CALL_BUY, max_dte=14` 只有 87 笔、21 个标的、8 个交易日。这不是“港股近月异动本来就少”，而是**归档只剩当前到期周期**。

因此：

1. **所有基于“历史近月异动”的统计（胜率、均值、p 值）都只在一个到期周期内成立**，不能外推，也不能当作长期规律。
2. `pi` 报告里“近月 DTE≤14、翻红 vs 翻绿、+7.0%、p≈0.0075（n=17）”这类结论，样本在时间上高度集中（几乎全在 2026-09），**存在严重的时间聚集偏差**。
3. 真正可用的部分：**当前正在发生的**近月信号（live 扫描），以及跨到期周期的“远月/长到期”统计；历史近月只能从别的数据源补（见下）。
4. 扫描器本身的逻辑（客户端 `dte_at_fill`、`MAX_DAY_NUM`、分页、时间过滤）**没有问题**，不需要改。

## 11. 修复建议

- **不要用**服务端 `dte` / `EXPIRY_DAYS` 做历史近月的判定；只用 `fill_time + strike_time`（代码 YYMMDD 兜底）。
- 若要回测历史近月，需要另找数据源（例如按合约逐日快照 / 自建每日异动落库，从今天开始积累），`get_option_event` 本身无法回溯已到期合约。
- 若继续用这份一年归档，请把结论限定为“远月（DTE 较大）异动”或“最近一个到期周期”的观察。

## 12. 无法排除项（诚实声明）

1. 我们只有 OpenD 这一个数据源，**无法直接量化“被清掉了多少条历史近月”**；只能证明“已到期合约的近月记录为 0”这一现象。
2. 官方文档（openapi.futunn.com `get_option_event` 页）**没有**写明“只保留当前挂牌合约 / 约一年归档”的限制；文档只写了 `MAX_DAY_NUM (0=当天,1=近2天…)` 与 `EXPIRY_DAYS 距到期天数`。该限制是从行为反推的。
3. `EXPIRY_DAYS` 的区间边界似乎被粗粒度化（`[0,5]` 与 `[0,7]` 相同、`[0,14]` 与 `[0,30]` 相同），具体取整规则未进一步实测。
4. 分页边界会产生少量重复行（CALL BUY 13 行、全类型 58 行）。已按业务主键去重，不影响结论；但若直接拿 `all_count` 当唯一记录数会略偏大。
